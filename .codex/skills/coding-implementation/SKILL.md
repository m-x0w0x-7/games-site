# Coding Implementation Skill

## 目的
ユーザー要求を安全かつ検証可能に実装し、変更の妥当性をテストで示して完了させる。

## 前提
- 作業開始前に対象リポジトリの `AGENTS.md`、`architecture.md`、`tasks.md` を確認する。
- 規約が競合する場合は、より制約の強い規約を優先する。
- 不明点が解消できない場合は実装を停止し、質問してから再開する。

## 実行手順
1. 要件整理
- 要件、完了条件、非対象を3行以内で明文化する。
- 影響ファイルと副作用リスクを列挙する。

2. テスト設計（Red前）
- 期待挙動をテスト観点へ分解する。
- 最初の1ケースだけ先に書く（最小失敗）。
- 失敗理由が仕様と一致することを確認する。

3. Red
- まず失敗するテストを書く。
- 実装コードはまだ増やさない、または最小限に留める。

4. Green
- 失敗テストを通す最小実装だけ追加する。
- 追加ロジックは将来拡張より現要件の充足を優先する。

5. Refactor
- テストが通っている状態を維持して構造改善する。
- Martin Fowlerの方針で小さく分割して進める。
- 各ステップ後にテストを再実行する。

6. セキュリティ確認
- 入力値の境界、未検証データ、依存追加の安全性を確認する。
- 危険なパターン（秘密情報の直書き、過剰権限、無制限処理）を排除する。

7. 完了報告
- 変更ファイル、テスト結果、残課題を簡潔に報告する。
- 実行できなかった検証があれば理由を明示する。

## コーディング規約
- JS/TSはシングルクォートを使う。
- class名はローワースネークケースを使う。
- id属性は極力使わない。
- JSで参照するclassは `js-` 接頭辞を付ける。
- 強制オプション（例: `-f`）は使わない。

## 出力フォーマット
以下の順で報告する。

1. `実装内容`: 何を変更したか
2. `テスト`: 実行コマンドと結果
3. `確認事項`: 残リスク・要確認点

## 例
### 例1
Input: 「5x5グリッドの反転ロジックを追加して」
Output: 失敗テスト作成 → 最小実装 → テスト成功 → 重複除去 の順で変更し、対象ファイルとテスト結果を報告。

### 例2
Input: 「このバグを直して」
Output: 再現テストを先に追加し失敗確認、修正後に回帰テストを通して報告。
